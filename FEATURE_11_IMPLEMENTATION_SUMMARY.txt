# FEATURE 11 IMPLEMENTATION SUMMARY: PARTIAL PAYMENTS & ADVANCE DEDUCTION

## Overview
Feature 11 enhances OrderLane Pro's payment processing to intelligently handle partial payments and automatically manage advance balance deductions. When customers have unallocated advance balances from previous overpayments, new incoming payments automatically apply these advances to outstanding invoices before collecting fresh cash, streamlining the payment-to-cash flow.

## Implementation Status: COMPLETE

### Core Files Created/Modified

#### Services (New)
1. **AdvanceDeductionService** (`app/services/payments/advance_deduction_service.rb`)
   - Analyzes customer's available advance balance
   - Calculates how much advance can be deducted from incoming payment
   - Returns deduction amount and remaining cash payment amount
   - FIFO ordering of advances (oldest first)
   - Cross-organization isolation (only considers advances from same org)

2. **AdvanceAllocationService** (`app/services/payments/advance_allocation_service.rb`)
   - Applies calculated advance deduction to outstanding invoices
   - Allocates to oldest invoices first (FIFO by invoice_date)
   - Creates PaymentAllocation records linked to source payment
   - Updates invoice paid_amount and outstanding_amount
   - Updates advance balance and status
   - Creates audit logs for tracking
   - Syncs credit account after allocation

#### Services (Modified)
- **ConfirmPaymentService** (`app/services/payments/confirm_payment_service.rb`)
  - Added `apply_advance_deduction()` method
  - Calls AdvanceDeductionService before standard FIFO allocation
  - Calls AdvanceAllocationService to apply advance if deductible amount > 0
  - Logs advance application via Credit::AuditLogger
  - Fully backward compatible (no advance = normal FIFO behavior)

## Feature Behavior

### Payment Flow (With Advance Deduction)
```
Customer makes payment of ₹500

Step 1: Check for advances
  Available: ₹200 (from previous overpayment)
  Deductible: ₹200 (entire advance less than payment)

Step 2: Apply advance to invoices
  Invoice 1 (oldest, ₹1000 due): Apply ₹200 → Now ₹800 outstanding
  Advance balance: ₹0

Step 3: Apply remaining cash (₹300) via FIFO
  Invoice 1 (₹800 outstanding): Apply ₹300 → Now ₹500 outstanding
  Unallocated: ₹0 (full payment allocated)

Result:
  - Invoice 1 paid ₹500 total (₹200 advance + ₹300 cash)
  - Outstanding reduced from ₹1000 to ₹500
  - Advance balance reduced from ₹200 to ₹0
  - All changes audited with actor, timestamp, amounts
```

### Partial Payment Handling
```
Customer has:
  - Invoice 1: ₹500 outstanding (10 days old)
  - Invoice 2: ₹300 outstanding (5 days old)
  - No advance balance

Payment: ₹400 (less than total outstanding)

Allocation (FIFO):
  1. Invoice 1: Apply ₹400 (oldest first)
     Outstanding: ₹100 remaining
  
  2. Unallocated: ₹0 (fully allocated)

Result:
  - Invoice 1: Partially paid (₹400)
  - Invoice 2: Unchanged (₹300)
  - No advance created (full allocation)
```

### Advance Creation (When Payment Exceeds All Outstanding)
```
Customer makes payment: ₹1000
Outstanding invoices: ₹700 total

FIFO allocation:
  1. Allocate ₹700 to all invoices
  2. Unallocated: ₹300

Advance creation:
  - Create AdvancePayment: ₹300 balance
  - Status: unapplied
  - Available for future payment deductions
```

## System Integration

### Data Flow
```
ConfirmPaymentService#call
  ├── [NEW] apply_advance_deduction
  │   ├── AdvanceDeductionService.call
  │   │   └── Calculate deductible amount based on available advances
  │   └── AdvanceAllocationService.call (if deduction > 0)
  │       ├── Allocate advance to oldest invoices (FIFO)
  │       ├── Update invoice paid/outstanding amounts
  │       ├── Update advance balance and status
  │       └── Audit log creation
  │
  ├── run_allocation (existing)
  │   ├── FIFO allocator or manual allocation
  │   └── Returns remaining payment amount
  │
  ├── write_allocations (existing)
  │   └── Create PaymentAllocation records
  │
  ├── create_advance_if_needed (existing)
  │   └── Create advance only if unallocated > 0 after all allocation
  │
  └── CreditSyncService.call
      └── Update customer credit metrics
```

### Query Options
- **AdvanceDeductionService**: Readonly analysis, no DB mutations
- **AdvanceAllocationService**: Read-write, creates allocations and updates balances
- **ConfirmPaymentService**: Orchestrates both services in a transaction

### Backward Compatibility
- Existing manual_lines parameter still works
- If no advances exist, behavior is identical to before (standard FIFO)
- Advance creation logic unchanged
- ApplyAdvanceService (manual advance application) still works alongside auto-deduction

## Database Schema (No Changes Required)

Existing tables are used:
- `payments` table: `allocated_amount`, `unallocated_amount` (already exist)
- `payment_allocations` table: Links payments to invoices (already exists)
- `advance_payments` table: Tracks advance balance and status (already exists)
- `audit_logs` table: Tracks all changes (already exists)

## Known Limitations & Future Enhancements

### Current Limitations
1. Auto-deduction is mandatory (if advances exist, they're used)
   - Future: Add customer preference flag to opt-out

2. No "reserve" advances (all advances eligible for auto-deduction)
   - Future: Tag advances as "reserved for specific invoice" or "unrestricted"

3. No advance refund policies
   - Future: Allow customers to request cash refund of advance balance

4. Advances can't be split during allocation
   - Future: Allow partial advance refund while keeping some for future use

### Recommended Future Work
- [ ] Customer preference: Enable/disable auto-advance deduction per customer
- [ ] Advance reservation: Reserve advance for specific invoice or limit usage
- [ ] Advance refund requests: Customer portal to request cash refund

- [ ] Advance expiration: Set expire dates on old advances

## Example Workflows

### Workflow 1: Simple Partial Payment
```ruby
# Customer has 1 outstanding invoice (₹1000) with no advance balance
payment = Payment.create!(customer: customer, amount: 600, status: 'draft')

result = Payments::ConfirmPaymentService.call(actor: user, payment: payment)

# Results:
# - Invoice outstanding: ₹400
# - Invoice paid: ₹600
# - Advance created: ₹0 (no unallocated)
# - No advance deduction needed (balance was 0)
```

### Workflow 2: Payment Using Auto-Deduction
```ruby
# Customer has:
#   - ₹200 advance balance (unapplied)
#   - 2 invoices: ₹500 (oldest) + ₹300 (newest) outstanding

payment = Payment.create!(customer: customer, amount: 400, status: 'draft')

result = Payments::ConfirmPaymentService.call(actor: user, payment: payment)

# Flow:
# 1. AdvanceDeductionService: ₹200 advance available
# 2. AdvanceAllocationService: Apply ₹200 to Invoice 1 (oldest)
#    - Invoice 1 now: ₹300 outstanding (was ₹500)
# 3. FIFO allocation: Apply remaining ₹400 cash to invoices
#    - Invoice 1: ₹300 allocated (now ₹0 outstanding)
#    - Invoice 2: ₹100 allocated (now ₹200 outstanding)
# 4. Results:
#    - Total invoices paid: ₹200 advance + ₹400 cash = ₹600
#    - Invoice 1: Fully paid
#    - Invoice 2: ₹200 remaining
#    - Advance balance: ₹0
```

### Workflow 3: Manual Allocation Override
```ruby
# Customer chooses specific invoices to allocate payment to
# (Bypasses advance auto-deduction if provided)

payment = Payment.create!(customer: customer, amount: 400, status: 'draft')

result = Payments::ConfirmPaymentService.call(
  actor: user,
  payment: payment,
  manual_lines: [
    { sales_invoice_id: inv1.id, amount: 250 },
    { sales_invoice_id: inv2.id, amount: 150 }
  ]
)

# Note: Manual allocation still triggers advance deduction check
# But the subsequent FIFO allocation respects customer's manual choice
```

## Troubleshooting Guide

### Advance not being deducted
**Check:** `AdvancePayment.where(customer: customer, status: 'unapplied').any?`
**Check:** `AdvancePayment.where(customer: customer, organization: org).any?`
**Fix:** Verify payment is being confirmed via ConfirmPaymentService (not raw PaymentAllocation.create)

### Advance balance not updating
**Check:** AuditLog.where(action: 'advance_auto_applied_to_invoice').last.changes['advance_balance_after']
**Fix:** Ensure AdvanceAllocationService completes successfully (check logs for errors)

### Multiple advances not using FIFO
**Check:** AdvancePayment.where(customer: customer).order(:created_at).pluck(:id)
**Check:** FIFO order should be by created_at in AdvanceDeductionService
**Fix:** Verify created_at timestamps are set correctly on advances

### Audit logs missing for advance application
**Check:** AuditLog.where(action: 'payment_advance_deduction_applied').any?
**Check:** AuditLog.where(action: 'advance_auto_applied_to_invoice').any?
**Fix:** Ensure ConfirmPaymentService.call is logging (AuditLogger initialized correctly)

### Invoice outstanding amount not reducing
**Check:** invoice.reload.outstanding_amount
**Check:** Verify payment is being confirmed (status: 'draft' → 'confirmed')
**Fix:** Check PaymentAllocation records created (should exist if payment confirmed)
