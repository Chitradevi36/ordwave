================================================================================
FEATURE 12 INTEGRATION SUMMARY: ApproveOrderService Integration
================================================================================

Overview:
---------
Feature 12 (Inventory Shortage Detection) has been successfully integrated into
the order approval workflow. When a customer or manager attempts to approve an
order, the system now automatically detects inventory shortages and prevents
approval until they are resolved.

Integration Points:
-------------------

1. ApproveOrderService (app/services/orders/approve_order_service.rb)
   Added: detect_and_handle_shortages() method
   
   Flow:
   ├─ 1. Validate order (original logic)
   ├─ 2. If decision is 'approved':
   │  └─ Detect shortages via Inventory::ShortageDetectionService
   │     ├─ If shortage detected → Return shortage_blocked response
   │     └─ If no shortage → Continue with approval
   ├─ 3. Transition order status (original logic)
   ├─ 4. Auto-assign to trip (original logic)
   ├─ 5. Create pick list (original logic)
   └─ 6. Reserve inventory (original logic)

   Key Points:
   - Shortage detection bypasses no automatic status change
   - Order remains in 'on_hold' status until shortage resolved
   - Rejection (decision='rejected') bypasses shortage check entirely
   - Dunning suspension check still happens first (before shortages)

2. API Controller Update (app/controllers/api/v1/sales_orders_controller.rb)
   Modified: approve action to handle shortage_blocked response
   
   Response Cases:
   ├─ OK Case (no shortage):
   │  ├─ Status: 200 OK
   │  ├─ Response: { status: 'approved', ... }
   │  └─ Order status changed to 'approved'
   │
   ├─ Shortage Blocked Case:
   │  ├─ Status: 422 Unprocessable Entity
   │  ├─ Response: {
   │  │   shortage_blocked: true,
   │  │   order: {...},
   │  │   shortage_detection: {
   │  │     has_shortage: true,
   │  │     shortage_items: [...],
   │  │     total_shortage_qty: N,
   │  │     total_shortage_value: D,
   │  │     resolution_options: ['refund', 'partial', 'reschedule', 'override'],
   │  │     message: "Order cannot be approved due to inventory shortages..."
   │  │   }
   │  │ }
   │  └─ Order status remains 'on_hold'
   │
   └─ Validation Error Case (original):
      ├─ Status: 422 Unprocessable Entity
      ├─ Response: { errors: [...] }
      └─ Order status unchanged

----------------------------

Step 1: Customer submits order

Step 2: Manager attempts to approve

Step 3: Manager/Customer chooses resolution (e.g., Partial Delivery)

Step 4: Manager approves again
   POST /api/v1/sales_orders/102/approve
   Request: { decision: 'approved' }

   Status: 200 OK
   {
     "data": {
       "status": "approved",

       ...

   }

Resolution Path Examples:
-------------------------

1. REFUND Path (Customer wants cancellation):
   POST /api/v1/sales_orders/102/resolve_shortage
   {
     "resolution_type": "refund",
     "notes": "Customer requests full refund"
   }
   Result: Order status → 'cancelled', Refund amount: 5000.00
   
   Then approval would fail (order is cancelled, can't approve)
   But API prevents re-approving cancelled orders

2. PARTIAL Path (Customer accepts partial delivery):
   POST /api/v1/sales_orders/102/resolve_shortage
   {
     "resolution_type": "partial",
     "notes": "Customer OK with 30 units now"
   }
   Result: Qty reduced, Refund: 2000.00, Status: 'partially_fulfilled'
   
   Then approve succeeds:
   POST /api/v1/sales_orders/102/approve → 200 OK (approve succeeds)

3. RESCHEDULE Path (Customer defers to future date):
   POST /api/v1/sales_orders/102/resolve_shortage
   {
     "resolution_type": "reschedule",
     "notes": "Stock arriving next week"
   }
   Result: Status: 'rescheduled', planned_delivery_date ≈ 7 days out
   
   Then approve succeeds:
   POST /api/v1/sales_orders/102/approve → 200 OK

4. OVERRIDE Path (Manager forces approval despite shortage):
   POST /api/v1/sales_orders/102/resolve_shortage
   {
     "resolution_type": "override",
     "notes": "VIP customer - expedite from supplier"
   }
   Result: Order immediately transitions to 'approved'
   
   Then approve still succeeds (redundant but harmless):
   POST /api/v1/sales_orders/102/approve → 200 OK

Decision Logic in ApproveOrderService:
---------------------------------------

```
if order.decision == 'approved':
  shortages = detect_shortages()
  if shortages.exists? AND shortages.not_resolved?:
    return {
      ok: false,
      shortage_blocked: true,
      shortage_detection: {
        has_shortage: true,
        shortage_items: [...],
        resolution_options: [...],
        message: "resolve shortage first"
      }
    }
  end
end

# If we reach here: either rejection, or shortages resolved/none
# Continue with normal approval flow
```

How Shortage Resolution Affects Approval:
------------------------------------------

After resolution, the approval will succeed IF:
1. Partial path: Order status changed to 'partially_fulfilled'
   → Approve transitions from 'partially_fulfilled' → 'approved'

2. Reschedule path: Order status changed to 'rescheduled'
   → Approve transitions from 'rescheduled' → 'approved'

3. Override path: Order status changed to 'approved' directly
   → Approve is no longer needed (already approved)

4. Refund path: Order cancelled
   → Order cannot be re-approved (validation prevents this)

Special Cases:
--------------

1. Rejection with shortage:
   POST /api/v1/sales_orders/102/approve
   {
     "decision": "rejected",
     "reason": "Credit limit exceeded"
   }
   Result: Order rejected immediately (no shortage check)
   
   Rationale: If rejecting anyway, no need to check inventory

2. Dunning suspension + shortage:
   - Dunning check happens FIRST in validate()
   - If dunning suspended, return error immediately
   - Shortage check never runs
   - Protects credit-compromised customers

3. Manual shortage resolution then validation error:
   If after resolving shortage, order fails other validation:
   - First call: shortage blocks it
   - Resolve shortage
   - Second call: other validation fails (e.g., missing delivery_date)
   - Returns validation error instead

Behavior Summary:
-----------------

BEFORE Integration:
├─ Order approval was instant (if no other blocks)
├─ Inventory shortages not checked until warehouse fulfillment
└─ Could create orders with insufficient inventory

AFTER Integration:
├─ Order approval checks inventory before transition
├─ Shortages detected → blocks approval, returns details
├─ Customer/manager must resolve → then reapprove
├─ Once resolved, approval proceeds normally
└─ Prevents warehouse surprises with unfullfillable orders

Error Handling:
---------------

Scenario: Inventory data inconsistency during approval
Flow:
1. Detect shortages → finds 20 short
2. Customer selects 'partial'
3. Resolve creates refund, updates qty
4. Reapprove called
5. Between resolution and reapprove, more inventory reserved elsewhere

Result:
- ApproveOrderService calls detect_shortages again
- Detects NEW shortage (inventory changed)
- Returns shortage_blocked again
- Customer sees updated shortage info
- Must resolve again

This is CORRECT behavior (conservative) - ensure inventory safety

No Data Loss:
-------------
- Shortage detection doesn't create/modify orders
- Only reads inventory and order data
- Shortage resolution modifies order status/lines (intentional)
- All changes audit-logged and reversible
- If need to undo: can manually revert via order edit + resolve_shortage

Performance Impact:
-------------------
Approval now includes:
- InventoryLevel lookup per order line (~10-50ms for most orders)
- Shortage calculation (~5-10ms)
- Total additional latency: ~20-60ms per approval

Mitigations if slow:
- Add database index on (organization, branch, product) in InventoryLevel
- Cache inventory levels per org/branch during off-peak
- Pre-detect shortages in background (pre-approval check)

Backward Compatibility:
-----------------------
- Existing approvals continue to work
- Shortage detection is additive (doesn't break existing flows)
- API response ALWAYS includes 'shortage_blocked' flag when applicable
- Response is 422 (Unprocessable Entity) which is reasonable for "cannot process now"
