# FEATURE 9 IMPLEMENTATION SUMMARY: DUNNING ENFORCEMENT

## Overview
Feature 9 implements automated enforcement of dunning-based account restrictions in OrderLane Pro. When customers have overdue invoices, the system applies escalating restrictions: Day 5 (soft block - flag for review), Day 10 (hard block - suspend account), Day 15 (escalation alert to operations).

## Implementation Status: COMPLETE

### Core Files Created/Modified

#### Jobs
- **DunningEnforcementJob** (`app/jobs/dunning_enforcement_job.rb`)
  - Daily background job (scheduled for 9 AM, after DunningSequenceJob at 8 AM)
  - Finds customers with overdue invoices (due_date < Date.current)
  - Applies escalating enforcement:
    - Day 5: Sets `credit_block_rule` to `soft_block`
    - Day 10: Sets `credit_block_rule` to `hard_block`, sets `dunning_suspended_at`
    - Day 15: Maintains suspension, alerts operations managers
  - Handles idempotency (won't re-suspend already suspended accounts)
  - Persists to `dunning_sequences` table for audit trail

#### Services
1. **Orders::ApproveOrderService** (`app/services/orders/approve_order_service.rb`)
   - Added validation check: Block order approval if `customer.dunning_suspended_at.present?`
   - Error message: "Cannot approve order: Customer account is suspended due to overdue invoices. Manual override required from finance team."
   - Allows rejection even for suspended accounts (for credit team workflow flexibility)

2. **Payments::ConfirmPaymentService** (`app/services/payments/confirm_payment_service.rb`)
   - Allows payments from suspended customers (important for dunning resolution)
   - Logs when payment is from suspended customer (action: `payment_from_suspended_customer`)
   - Creates notification for finance team flagging payment for manual review
   - Records suspension details in audit log (reason, invoice ID, dates)

3. **Invoice::GenerateFromDeliveryService** (`app/services/invoice/generate_from_delivery_service.rb`)
   - Allows invoice generation for suspended customers (billing must continue)
   - Logs invoice creation for suspended customer (action: `invoice_generated_for_suspended_customer`)
   - Creates notification for finance team for manual review
   - Useful for tracking what customers owe despite account suspension

#### Migrations

## Feature Behavior

### Day 5 Enforcement (Soft Block)
```
Trigger: Invoice overdue for 5 days
Action: Set credit_block_rule = 'soft_block'
Effect: Orders can still be approved (not hard-blocked)
Notification: Finance team gets "Dunning Enforcement - day_5" alert
Audit Log: Soft block enforcement recorded
Idempotent: Won't reapply if already soft_blocked
```

### Day 10 Enforcement (Hard Block + Suspension)
```
Trigger: Invoice overdue for 10 days
Action: 
  1. Set credit_block_rule = 'hard_block'
  2. Set dunning_suspended_at = Time.current
  3. Set dunning_suspension_reason = 'day_10'
  4. Set dunning_suspension_invoice_id = invoice.id
Effect: Orders CANNOT be approved (ApproveOrderService blocks them)
Notification: Operations managers get URGENT alert
Audit Log: Suspension recorded with all relevant details
Idempotent: Won't re-suspend if already suspended
Workaround: Finance can manually clear dunning_suspended_at to lift restriction
```

### Day 15 Enforcement (Escalation)
```
Trigger: Invoice overdue for 15 days
Action: Send ESCALATION alert to operations managers
Effect: Maintains hard_block and suspension (no change to restrictions)
Notification: 
  - All operations managers get "Critical: Highly Overdue Account" alert
  - SMS sent to first manager (if Twilio enabled and phone available)
Audit Log: Escalation action recorded
Idempotent: Won't re-alert if escalation_15day_alert_sent already logged
```

### Payment Processing for Suspended Customers
```
Trigger: Payment received from suspended customer
Processing: 
  1. Payment is processed normally (allowed to help resolve dunning)
  2. FIFO allocation applies payment to oldest invoices
  3. Audit log created: payment_from_suspended_customer
  4. Finance team notified (HIGH severity) for manual review
Business Value: Allows customers to make payments while blocked from new orders
```

### Invoice Generation for Suspended Customers
```
Trigger: Invoice needs to be created for suspended customer
Processing:
  1. Invoice is generated normally (billing must continue)
  2. Audit log created: invoice_generated_for_suspended_customer
  3. Finance team notified (MEDIUM severity) for review
Business Value: Tracks what customers owe despite account suspension
```

## System Integration

### DunningSequenceJob (Day 1, 5, 10, 15 - 8 AM)
- Sends email notifications on dunning timeline
- Sets enforcement_level in dunning_sequences table (day_1, day_5, day_10, day_15)
- Modified to use correct field names: dunning_suspended_at (not account_status)

### DunningEnforcementJob (Daily - 9 AM)
- Runs AFTER DunningSequenceJob
- Reads enforcement_level from dunning_sequences
- Applies hard credit blocks and account suspension
- Notifies finance/operations teams

### Credit Engine Integration
- DunningEnforcementJob uses existing credit_block_rule field
- No changes needed to credit evaluation logic
- Dunning suspension is separate from and complementary to negative credit decisions

### Notification System
- Uses existing Notifications::CreateService
- Creates audit logs via Credit::AuditLogger
- Supports in-app notifications + email + SMS (Twilio)

### Sidekiq Job Queues
- DunningEnforcementJob runs on 'operations' queue
- Retry: 2 times on failure
- Recommended: Set up cron job to trigger at 9 AM daily

## Database Schema Changes

### Customers Table Additions
```sql
ALTER TABLE customers ADD COLUMN dunning_suspended_at TIMESTAMP;
ALTER TABLE customers ADD COLUMN dunning_suspension_reason VARCHAR(50);
ALTER TABLE customers ADD COLUMN dunning_suspension_invoice_id VARCHAR(50);

CREATE INDEX idx_customers_dunning_suspended_at ON customers(dunning_suspended_at);
```

## Configuration & Deployment

### Required Setup
1. **Database Migration**
   ```bash
   bundle exec rake db:migrate
   ```

2. **Cron Job Configuration**
   ```ruby
   # config/schedule.yml (Sidekiq Scheduler)
   dunning_enforcement_job:
     cron: '0 9 * * *'  # Daily at 9 AM (must be after DunningSequenceJob at 8 AM)
     class: DunningEnforcementJob
     queue: operations
   ```

3. **Optional: Twilio SMS for Day 15 Escalation**
   - Ensures TwilioClient credentials are set (.env)
   - Phone numbers populated on finance/operations manager User records
   - If not configured, SMS is skipped (falls back to in-app notification)


## Rollout Strategy

### Recommended Phased Rollout (4 weeks)
1. **Week 1: Soft Block Only**
   - Set `dunning_enforcement_enabled = true` but only apply Day 5 enforcement
   - Monitor: Check soft_block application, finance notifications
   - Measurement: % of customers flagged, notification delivery success

2. **Week 2: Hard Block + Suspension (Low Risk Segment)**
   - Enable Day 10 enforcement for top 10% at-risk customers
   - Monitor: Order rejection rates, customer complaints, payment collection
   - Measurement: Orders blocked, payment responses, dunning sequence completion

3. **Week 3: Hard Block + Suspension (Scale to 50%)**
   - Expand to customers with >15 days overdue
   - Monitor: Same metrics as Week 2, add escalation effectiveness
   - Measurement: Dunning sequence progression, suspension clearance rate

4. **Week 4: Full Production**
   - Enable for all customers with overdue invoices
   - Continuous monitoring: Core metrics + dunning lifecycle

## Known Limitations & Future Enhancements

### Current Limitations
1. Soft block (Day 5) doesn't auto-prevent orders - requires human approval
   - Future: Could integrate with credit engine to auto-hold orders

2. Dunning suspension is binary - no intermediate states
   - Future: Could add "warning" state (Day 7), "review" state (Day 12)

3. No automatic suspension lift after payment
   - Future: Could auto-clear dunning_suspended_at when invoice is fully paid

4. Day 15 escalation only alerts managers
   - Future: Could auto-escalate payment plans, dunning to collection agency

### Recommended Future Work
- [ ] Auto-clear suspension when invoice is paid in full
- [ ] Partial payment plans (accept partial payment to lift suspension)
- [ ] Appeal workflow (customer can request suspension lift)
- [ ] Integration with SMS/email payment links (charge + suspension lift)
- [ ] Dunning escalation service (integrate with external collection agency)

## Troubleshooting Guide

### Order won't approve for non-suspended customer
**Check:** `customer.dunning_suspended_at` is nil
**Fix:** Run `customer.update(dunning_suspended_at: nil)` to explicitly clear

### Job not running / enforcement not applying
**Check:** Sidekiq scheduler is running: `bundle exec sidekiq -c 1`
**Check:** Cron job is configured in `config/schedule.yml` or Sidekiq-specific scheduling
**Fix:** Run manually: `DunningEnforcementJob.perform_now`

### Finance notifications not sent
**Check:** Notification.where(notification_type: 'dunning_enforced_day_10').count > 0
**Check:** Finance users exist with role='finance' or role='admin'
**Fix:** Create test user: `create(:user, role: 'finance')`

### Payment from suspended customer not flagged
**Check:** Audit log: `AuditLog.where(action: 'payment_from_suspended_customer').last`
**Check:** Customer.notification_data includes 'payment_processed_while_suspended'
**Fix:** Ensure ConfirmPaymentService.call is being used (not raw PaymentAllocation.create)

### Day 15 escalation SMS not sent
**Check:** TwilioClient.enabled? returns true
**Check:** Operations manager has phone number set
**Check:** Twilio credentials in .env (TWILIO_ACCOUNT_SID, TWILIO_AUTH_TOKEN, TWILIO_PHONE_NUMBER)
**Fix:** Set phone manually: `user.update(phone: '+91XXXXXXXXXX')`
