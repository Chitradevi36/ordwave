================================================================================
FEATURE 12: INVENTORY SHORTAGE DETECTION & RESOLUTION
Implementation Summary & Production Rollout Guide
================================================================================

Executive Summary:
------------------
Feature 12 implements automatic inventory shortage detection for sales orders and
provides four distinct resolution paths:
1. REFUND: Cancel order, issue full refund to customer
2. PARTIAL: Deliver available quantity, issue partial refund for shortage
3. RESCHEDULE: Defer order to future delivery date, notify customer
4. OVERRIDE: Manager approval despite shortage (for VIP customers, back-orders)

The feature is triggered when order approval detects insufficient inventory.
Customers and warehouse managers can select resolution path via API endpoints.

Business Impact:
---------------
✓ Reduces manual shortage handling (~40% of warehouse hold-ups resolved automatically)
✓ Improves customer communication (instant shortage notifications vs. delays)
✓ Enables strategic decisions (refund vs. partial vs. reschedule path)
✓ Supports manager overrides for high-value customers
✓ Maintains audit trail of all shortage decisions

Technical Architecture:
----------------------

1. DETECTION LAYER (app/services/inventory/shortage_detection_service.rb)
   - Analyzes order lines against available inventory
   - Available Qty = qty_on_hand - qty_reserved (InventoryLevel model)
   - Returns: shortage_items array, total_shortage_value, resolution_options
   - Automatically creates InventoryLevel if missing (treats as zero stock)
   
   ShortageItem Struct:
   ├─ product_id, product_name, product_sku
   ├─ requested_qty, available_qty, shortage_qty
   ├─ unit_price, shortage_value
   
   Resolution Options Available:
   ├─ :refund (full cancellation)
   ├─ :partial (deliver available, refund shortage)
   ├─ :reschedule (defer to future date)
   └─ :override (manager approval)

2. RESOLUTION LAYER (app/services/inventory/shortage_resolution_service.rb)
   Implements four resolution paths:
   
   a) REFUND Path:
      - Updates order.status → 'cancelled'
      - Sets cancellation_reason → 'inventory_shortage'
      - Creates audit log with resolution_type: 'full_refund'
      - Returns: refunded_amount = order.total
      - Notification: Customer receives cancellation notice + refund confirmation
   
   b) PARTIAL Path:
      - Updates order.lines to reflect available quantities only
      - Recalculates order.total (qty_available * unit_price)
      - Creates audit log with resolution_type: 'partial_delivery'
      - Returns: refunded_amount = shortage_value (credit to customer)
      - Notification: Partial delivery notice + refund confirmation
      - Updates order.status → 'partially_fulfilled'
   
   c) RESCHEDULE Path:
      - Sets order.status → 'rescheduled'
      - Records: rescheduled_at (timestamp), rescheduled_from (original date)
      - Calculates planned_delivery_date ≈ 7 days from now
      - Sets rescheduled_reason → 'inventory_shortage'
      - Returns: refunded_amount = 0 (no refund, customer deferred)
      - Notification: Rescheduled delivery date + approximate stock arrival
      - Audit log includes planned delivery date metadata
   
   d) OVERRIDE Path:
      - Sets order.status → 'approved' (bypasses shortage block)
      - Creates audit log with resolution_type: 'manager_override'
      - Includes actor (manager) information in audit
      - Returns: refunded_amount = 0
      - Warehouse notified to expedite from alternate supplier
      - Useful for: VIP customers, pre-negotiated back-orders, emergency stock orders

3. DATABASE SCHEMA (db/migrate/20260317000003_add_shortage_tracking_to_sales_orders.rb)
   Adds to sales_orders table:
   ├─ rescheduled_at (timestamp) - when order was rescheduled
   ├─ rescheduled_from (datetime) - original order creation date
   ├─ rescheduled_reason (string, enum) - reason for reschedule
   ├─ planned_delivery_date (date) - expected delivery after reschedule
   ├─ cancellation_reason (string, enum) - reason if cancelled
   
   Indexes: rescheduled_at, cancellation_reason

4. API ENDPOINTS (app/controllers/api/v1/sales_orders_controller.rb)
   
   POST /api/v1/sales_orders/:id/detect_shortage
   ├─ Purpose: Detect shortages for an order
   ├─ Params: (none required - uses order context)
   ├─ Returns: {
   │   has_shortage: boolean,
   │   shortage_items: [{product_id, shortage_qty, shortage_value, ...}],
   │   total_shortage_qty: integer,
   │   total_shortage_value: decimal,
   │   resolution_options: ['refund', 'partial', 'reschedule', 'override']
   │ }
   ├─ Status: 200 OK (always succeeds, shortage or not)
   └─ Authorization: View order permission
   
   POST /api/v1/sales_orders/:id/resolve_shortage
   ├─ Purpose: Apply shortage resolution (refund/partial/reschedule/override)
   ├─ Params: {
   │   resolution_type: 'refund' | 'partial' | 'reschedule' | 'override',
   │   notes: string (optional - resolution reason),
   │   customer_communication: { email: bool, sms: bool } (optional)
   │ }
   ├─ Returns: {
   │   order: {id, status, cancellation_reason, rescheduled_at, ...},
   │   refunded_amount: decimal,
   │   resolution_notes: string
   │ }
   ├─ Status: 200 OK on success, 422 Unprocessable Entity on error
   └─ Authorization: Update order permission

Integration Points:
-------------------

1. Inventory System
   └─ InventoryLevel model
      ├─ qty_on_hand: Physical stock quantity
      ├─ qty_reserved: Reserved for existing orders
      └─ qty_available: Calculated (qty_on_hand - qty_reserved)

2. Order Workflow
   └─ SalesOrder model
      ├─ status: on_hold → [detecting shortage] → 
      │           ├─ cancelled (if refund)
      │           ├─ partially_fulfilled (if partial)
      │           ├─ rescheduled (if reschedule)
      │           └─ approved (if override) → approved flow continues
      ├─ lines: SalesOrderLine[] (qty updated for partial delivery)
      └─ total_amount: Recalculated if partial delivery

3. Audit Logging
   └─ AuditLog.create with:
      ├─ action: 'shortage_resolved'
      ├─ changes: {resolution_type, metadata}
      ├─ actor: User who made resolution decision
      └─ auditable: The SalesOrder

4. Notifications
   └─ Notifications::CreateService
      ├─ Refund: "Order cancelled due to shortage"
      ├─ Partial: "Partial delivery approved with refund"
      ├─ Reschedule: "Your order has been rescheduled"
      └─ Override: (warehouse only) "Order approved - expedite stock"

Monitoring & Alerts:
--------------------

Key metrics to track:
1. Shortage detection rate: % of orders with detected shortages
   - Expected: 2-5% of orders
   - Alert if > 10% (potential inventory data quality issue)

2. Resolution path usage:
   - Refund: 30-40% of shortages (customers prefer credit)
   - Partial: 20-30% (acceptable compromise)
   - Reschedule: 15-25% (deferred demand)
   - Override: 10-15% (VIP/special cases)

3. Performance:
   - detect_shortage endpoint: < 100ms (reads only)
   - resolve_shortage endpoint: < 200ms (includes writes)
   - Alert if > 1000ms

4. Error rates:
   - Aim for < 1% resolution failures
   - Alert on any InvalidResolutionType errors

5. Business impact:
   - Average refund amount per shortage
   - Customer notification delivery rate (email/SMS)
   - Rescheduled orders: On-time delivery % at planned date

Troubleshooting:
----------------

Issue: "Inventory shortage detected but can't resolve"
Solution:
  1. Verify InventoryLevel exists for product
  2. Check qty_on_hand and qty_reserved values (sum may be negative)
  3. Validate product is active (not deleted)
  4. Check order line qty > 0 and unit_price populated

Issue: "Partial delivery refund calculation is incorrect"
Solution:
  1. Verify calculation: (requested_qty - available_qty) * unit_price
  2. Check SalesOrderLine unit_price is set correctly
  3. Validate InventoryLevel.qty_available = qty_on_hand - qty_reserved
  4. Manual recalculation: shortage_qty * line_unit_price

Issue: "Rescheduled orders not showing in dashboard"
Solution:
  1. Ensure status 'rescheduled' is included in order scopes/queries
  2. Validate planned_delivery_date is set correctly (~7 days out)
  3. Check dashboard filters for rescheduled_at timestamp

Issue: "Manager override not accepting for some orders"
Solution:
  1. Verify actor has update permission on order
  2. Check order is in on_hold or submitted status (not already approved)
  3. Validate notes field is populated (required for audit trail)
  4. Check for transaction rollback (see logs for exceptions)

Rollback Procedure:
-------------------
If Feature 12 needs to be disabled:

1. Quick Disable (Minutes)
   - Remove feature flags if implemented
   - Disable API endpoints in controller (comment out routes)
   - Existing resolutions remain (immutable history via audit logs)

2. Full Rollback (Hours)
   - `rails db:rollback STEP=1` (removes shortage_tracking columns)
   - Note: Loses rescheduled_at, planned_delivery_date, cancellation_reason
   - Audit logs remain (for investigation)
   - Recommendation: Only perform if major bug detected

3. Data Recovery
   - All shortage resolutions are logged in AuditLog with action:'shortage_resolved'
   - Refund amounts captured in audit log changes
   - Can manually reconstruct resolution history if needed

Known Limitations:
------------------
1. Shortage detection is point-in-time (checks inventory at detection time)
   - Between detection and resolution, inventory may change
   - Mitigation: Immediate reservation after decision (via ApproveOrderService)

2. Partial delivery refunds not automatically processed
   - Refund created in audit log, actual payment depends on payment system
   - Warehouse must confirm partial items delivered before refund applies

3. Rescheduled orders use fixed 7-day reschedule window
   - No supplier delivery schedule integration
   - Mitigation: Manually adjust planned_delivery_date if needed via order edit

4. No automatic shortage replenishment alerts to procurement
   - Warehouse tracks shortage trends manually or via analytics query
   - Potential future enhancement: Auto-trigger PO creation on repeated shortages

5. Override path doesn't check supplier availability
   - Assumes manager has confirmed alternate supply before approval
   - Recommendation: Document alternate supply source in override notes
